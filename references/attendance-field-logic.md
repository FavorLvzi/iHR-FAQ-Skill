### 日报自定义字段（D34+，★必须关联 #96 查询，2026-08-13 宿主实测补）

日报除标准字段（D1~D33）外，还有**企业自定义字段**，存储在 `dailyCustomField`（UUID→值映射）。

**查询方法（两接口必须配合）**：
1. **#93 日报** → 返回 `dailyCustomField`（**UUID→值**映射）
2. **#96 日报自定义字段定义** → 返回字段定义（**id→名称/formula**）
3. 两者通过 **UUID 关联** → 得到"字段名称 → 公式逻辑 → 当日值"完整链路

**输出要求（宿主 AI 必做）**：
- 回答日报字段问题时，**必须同时查 #96**，把 UUID 映射为可读字段名（否则只看到一串 UUID，无法回答）
- 展示自定义字段时列出：**字段名称、公式逻辑、当日值**
- 公式引用语法：`出勤$字段名`（日报标准字段）/ `日报自定义字段$字段名`（其他自定义字段）/ `其他$字段名` / `员工基本信息$字段名`

> 规格见 `references/api-reference.md`「#93 vs #96 关联（★必须）」。

### 实际出勤小时数 D3 的完整算法（两档）

**A. 取出勤交集班次的员工**
1. 签退 / 签到时间与排班的交集 − 休息时段
2. 休息日是否计入实际出勤 → 看考勤设置（计入则按规则计入，不计入则不计入）
3. ①或② + 出差 / 外出与班段的交集
4. 结果与应出勤小时数对比：**大于取应出勤，小于取实际出勤**

**B. 取实际打卡的员工**
1. 上班日：签退 − 签到 − 班次内休息时间 − 班次外休息时间
2. 休息日是否计入实际出勤 → 看考勤设置
3. ①或② + 出差 / 外出时长
4. 封顶同 A（注：图 B 第 4 条"不论大于小于等于取实际出勤"疑为笔误，按封顶理解，与 A 对称）

> 核心公式表达：`实际出勤小时数 = min(计算值, 应出勤小时数)`，超出部分进入加班 / 延时工时 / 深夜工时。

## 三、已证实的关键结论（供回答时引用）

1. **应出勤小时数 = 班次决定**（例：朝九晚五 → 8h，扣班段内休息）。
2. **实际出勤小时数 = 打卡 ∩ 班次 − 休息，封顶 min(值, 应出勤小时数)**。
3. **实际出勤天数 = 实际出勤小时 ÷ 应出勤小时，比值 > 1 时取 1**（两字段共用同一条计算链，天数只是小时的比值派生）。
4. **缺勤小时数 = 应出勤 −（出差/外出/请假 + 班段内休息）**，交叉时段去重。
5. 全天缺卡 → 归为"缺勤"，覆盖迟到早退判定；实际出勤小时 = 0。
6. 休班次 / 跨天 / 综合工时等复杂场景，计算规则走 **考勤 → 考勤设置 → 复杂场景规则设置**，不在上述默认逻辑内。

## 三·五、假期额度计算逻辑（2026-08-04 实测确认）

**核心公式**：`当前余额 = 发放额度 − 已用 + 结转 − 作废/到期`

| 环节 | 数据来源 | 说明 |
|------|---------|------|
| 发放额度（年假） | OpenAPI #82（当年发放/结转 6 字段） | 唯一有明细拆分的假期 |
| 发放额度（非年假） | **二方 #116 额度变更流水** | 按 `operateReason` 逐条溯源（如调休来自"加班单据初始化导入"+"修改加班单"） |
| 已用 | OpenAPI #77 休假单 或 二方 #115 使用记录 | 已生效休假单时长汇总 |
| 当前余额 | OpenAPI #80（仅 availableLimit） | 全假期类型可用 |
| 结转/作废 | 二方 #116 流水（operateReason 含"结转/作废/到期"） | 年假常见：结转到期日作废 |

**关键实测结论**：
1. **年假完整链路可还原**：#82 当年发放 + 结转 + 余额，与 #116 流水交叉印证（如 2025+5 → 2026+5 → 结转+5 → 可用5）。
2. **非年假发放额度只能靠 #116 流水**：#80 只返回 `availableLimit`，无计算过程；调休的额度来源在流水中逐条可见（加班单导入 +20h / 删除 -20h / 员工申请调休 -8h）。
3. **流水可以全量拉**：#116 参数仅需 `staffId + vacationId`（r_id/u_id 后端不校验），员工清单取 #1、假期类型取 #79，双层循环即可查全员。
4. **边界**：发放额度 ≠ 余额 + 已用的简单相加，中间有结转/作废/到期影响；完整回答应给出流水明细而非只报差额。
5. **单位**：#79 `smallestUnit` 对按小时计假期是**分钟数**（病假120/哺乳假60/季度假30）；`dayHourConversion` 有值才显示"1天=X小时"。

## 三·六、加班转薪资额度计算逻辑（2026-08-05 实测确认）

**核心业务机制**：加班单实际小时 → 按规则转入"转薪资额度"；**只有薪资模块锁定后额度才真正被使用，取消锁定（考勤引用取消）则返还**。

**数据链路**：

| 环节 | 数据源 | 说明 |
|------|--------|------|
| 加班总额度 | #83 加班单 `overtimeHours`（实际小时，生效单） | 加班产出原始量 |
| 转调休额度 | #86 结转 `adjustRestHour` | 加班转调休部分 |
| 转薪资额度 | #86 结转 `salaryHour`（总额）/ `salaryUsedOvertimeHour`（已用）/ `surplusHour`（剩余） | 员工级结余（OpenAPI，需 OAuth Bearer；SK token 宿主环境不可调） |
| **锁定/解锁账本** | **#117 `pageSalaryTransferChangeRecord`**（二方） | changeReasonType 三枚举：SALARY_PLAN_CHANGE 薪资方案考勤取数（=锁定/解锁）/ OVERTIME_FORM_CHANGE 加班单变更 / ADJUST_EXPIRED_TRANSFER 调休过期转薪资 |
| 加班单变更流水 | #116/#OL | 增删改/重算痕迹 |

**★ 净锁定判定（核心判别规则，防误判）**：
- **锁定 → deltaAmount 为负**（额度减少）；**解锁 → 为正**（返还）；加班单变更 → 按单据联动增减
- **判定"额度是否足够锁定"必须用净锁定** = 毛锁定 − 解锁（如毛锁 14h − 解锁 8h = 净 6h），**不能用毛锁定**（否则"先锁后解"的正常操作会被误判为超用）
- 结论：净锁定 ≤ 转薪资总额度（#86 salaryHour）→ 充足；否则额度不足（需核查加班单变更是否回收了转薪资额度）

**#117 接口要点**：POST `/web/gateway/attendance/api/overtimeMonthlyAccount/pageSalaryTransferChangeRecord`，分页参数 **`{"current":1,"size":10}`**（用 `page` 会导致 content 为空）；`staffId`/`staffIds` 参数暂不生效（返回登录人范围数据）；changeDetail 为自然语言含方案名+月份（"薪资「测试薪资方案」-2026年01月锁定1.00小时"）。

## 三·七、薪资字段计算逻辑（问题4，2026-08-06 实测闭环）

**★ 问题4 的核心定位（用户定案）**：回答的是**"这个数怎么算出来的"（计算逻辑）**，**不是"这个数是多少"（结果）**——结果在系统页面/API 里直接可查，AI 的增值在**公式解读**：拿公式 → 讲清楚逻辑 → 用结果验证。交付形态是"逻辑解读"，不是"结果台账"。

**机制**：薪资字段**无内置逻辑、全部公式定义**（与考勤根本不同，见 `field-formula-source.md` 六）。

**★ 计算逻辑解读四步法（问题4 核心输出形态）**：

```
1. 拿公式    → 二方 companySalaryfieldMetas/list（每项 formula 明文）
2. 拆解逻辑  → 用 formula-language.md 解读：函数含义/变量依赖/IF 分支/表名$字段
3. 讲清楚    → 用中文讲"这个字段 = 哪些上游字段怎么组合"，标注配置项（承担方/税率表等）
4. 值验证    → #67 拿该员工该月实际值代入公式，确认解读正确（可复现即解读正确）
```

**★ 复杂公式值链递归解读法（问题4 深化，客户公式多为 A+B+C−D+IF(x,y,z) 形态）**：

```
1. 识别形态   → 最终字段 = 各分项加减组合 + IF 分支，列出全部分项
2. 逐项递归   → 每个分项若自身是公式 → 继续下钻，直到"输入值/表引用/配置值"（值链终点）
3. IF 分支取舍 → 标注判定条件（纳税人身份/承担方等配置字段）+ 当前实际取值走哪个分支 + 为什么
4. 组合还原   → 各分项取值代入公式，验证 = 最终值
5. 防误判     → IF 判定用的配置字段（如承担方）不在 #67 summaryData——
                分支取舍按"实际扣减值"反推（扣了 1040 社保 → 承担方必为个人）；
                值链终点（STAFF_SAL$ / SIHF$ 等表引用）不再下钻，标注"表/配置来源"
```

**★ 值链递归解读实例（实发合计 totaltakehomepay，员工C 2025-01，37996.85）**：
- 形态：`A + B − C + D + E + F` = 实发工资 + 税后报销 − 税后扣款 + 实发年终 + 实发劳务 + 实发补偿
- 主分项 A（netpaysalary）= `grosssalary − IF(社保承担方=单位,0,scee) − IF(公积金承担方=单位,0,hfee) − 当月个税` → 42333.66 − 1040 − 2400 − 896.81 = 37996.85 ✅
  - 下钻 grosssalary = IF(居民, grossincome − 年终 − 补偿) → 42333.66 ✅
  - 下钻 grossincome = salarytotal + ... − 减项 → 42333.66 ✅
  - 下钻 salarytotal（工资类加项求和）→ 值链终点
  - scee/hfee = SIHF$ 表引用（社保/公积金表）→ 值链终点
- 个税分项（thismonthshouddeductsalarytax = 896.81）：
  - thismonthsalarytax = IF(居民, salarytax − 上月累计, 当月速算) → 1月无累计 = 896.81 ✅
  - salarytax = taxablesalary × 税率 − 速算扣除 → 29893.66 × 3% − 0 ✅
  - taxablesalary = MAX(0, 累计应发 − 社保 − 公积金 − 附加 − 减除 − 养老金) → 29893.66 ✅
- 年终奖分项 D（netpayannualbonus）= yearendbonustotal − yearendbonustax → 本月无 = 0
- **IF 分支取舍示例**：`IF(社保承担方="单位",0,scee)` —— 实际扣了 1040 → 反推承担方=个人，走 scee 分支；`IF(纳税人身份="居民",...)` —— taxrole=居民，走居民分支

**数据链路（支撑解读）**：

| 环节 | 数据源 | 说明 |
|------|--------|------|
| ① 公式内容 | **二方 `POST /gateway/payroll/api/companySalaryfieldMetas/list`** | 185 项每项 `formula` 明文（如 `=STAFF_SAL$basesalary`） |
| ② 公式解析（可选） | 二方 `GET /gateway/component/manage/api/component/table/manage/enable?code=payroll.table.companysalaryfield` | exprItems token 流校验 |
| ③ 语法解读 | `references/formula-language.md` | 函数/`表名$字段`/`{数组}` |
| ④ 值验证 | OpenAPI **#67** 按员工+方案+年月 | 91 项值 `{'v':'xxx'}` |

**★ 典型计算逻辑链（员工A 2025-08 实测，逐环解读）**：

- `grossincome`（应发合计）= `salarytotal + bonustotal + compensationtotal + yearendbonustotal + pretaxallowancetotal − pretaxdeductiontotal` → 读作："本月全部税前加项之和减去税前减项"
- `grosssalary`（当月应发月薪合计）= IF(居民, `grossincome − yearendbonustotal − compensationtotal`) → 读作："居民身份下，应发合计去掉年终奖与补偿金（这两类走单独计税）"
- `taxablesalary`（累计应纳税所得额）= MAX(0, IF(居民, `cumulativegrosssalary − IF(社保承担方=单位,0,cumulativescfee) − IF(公积金承担方=单位,0,cumulativehffee) − totaltaxablecumulcurmonth − cumulativesalarytaxdeducat − accumPersonalPension`, `grosssalary − salarytaxdeduction`)) → 读作："累计应发 − 个人承担社保/公积金 − 专项附加 − 累计减除(5000×月数) − 个人养老金，下限 0；非居民走当月口径"
- `salarytax`（当月个税）= `taxablesalary × salarytaxrate − salarytaxreduce` → 读作："应纳税所得额套税率表（VLOOKUP 累计档位）乘税率减速算扣除数"

**★ 典型方案深度解读（"工资薪金+年终奖"，员工C 2025-01，公式链 6/6 验证）**：
- 完整链：basesalary/positionsalary（薪资档案输入）→ salarytotal（加项求和）→ grossincome（应发合计=加项−减项）→ grosssalary（剔除年终奖/补偿，单独计税）→ salarybeforetax（减个人社保公积金）→ taxablesalary（累计预扣：累计应发−社保−公积金−专项附加−累计减除−养老金，下限0）→ salarytax（累计税率表 VLOOKUP）→ netpaysalary（−社保−公积金−当月个税）→ totaltakehomepay（+税后年终/劳务/补偿）
- **年终奖链路（方案特有）**：`taxableannualbonusspecial = IF(居民, yearendbonustotal)`（全额计税）→ `yearendbonustax = taxableannualbonusspecial × annualbonustaxrate − annualbonustaxreduce`（**年终奖专属税率表**，单独计税）→ `netpayannualbonus = yearendbonustotal − yearendbonustax`
- **跨方案引用**：`'%based_on_salaryplan_name%'!totaltakehomepay` 等——引用本方案他期/其他方案的值（如合并年终奖金=上期年终+本期年终）
- **逐月个税爬升解释**：应纳税所得额是累计值，年末累计额高、税率档位高（员工C 2025：1月 3% 896.81 → 11月 30% 50287.57）——累计预扣法的直观体现
- 验证 6/6：grossincome 42333.66 ✅ / grosssalary ✅ / taxablesalary 29893.66 ✅ / salarytax 896.81 ✅ / netpaysalary 37996.85 ✅ / totaltakehomepay ✅

**★ 解读要点（判别规则）**：

## 三·八、考勤异常排查（问题6，双视角 + 打卡前后分流）

**前置①**：先按 SKILL.md「视角识别」判断提问者是管理员/HR 还是员工本人。
**前置②（分流判断）**：先判断异常发生在**打卡前还是打卡后**，决定走哪条路径：

- **打卡前被拦**（app 打不了卡、显示"不在打卡范围内/无法定位"）→ 走 **C 路径 · 打卡规则配置咨询**——员工反馈 + 打卡规则常识即可回答，**无需 API 溯源**（打卡未发生，无记录/无日志可查）
- **打卡后异常**（缺勤、实际出勤/打卡不符）→ 走 A/B 路径（数据溯源）

### C 路径 · 打卡前异常（规则配置咨询，无需 API）

目标：回答"为什么打不了卡"，定位打卡规则配置问题。

**判断依据（关键）**："打卡前被拦"发生在打卡动作**之前**（app 端校验拦截），此时员工**未产生打卡记录** → #91 无数据、#110 无操作日志——**不是数据异常，是打卡规则/入口配置问题**，凭员工反馈即可定位。

**打卡前异常的两个子场景（先分流）**：
- **子场景一：有打卡入口但打不了**（点打卡提示"不在打卡范围内"）→ 走「鱼骨图① 定位问题」
- **子场景二：没有打卡入口**（app 找不到打卡按钮，**刚入职员工常见**）→ 走「鱼骨图② 入口未生效」

**★ 鱼骨图排查法（本 skill 独有，打卡前异常的核心方法论）**：

### 鱼骨图① 有入口但"不在打卡范围"（定位问题）

把"不在打卡范围"作为问题鱼头，从**四大类原因**（鱼骨刺）系统排查，每类下列具体因子。**排查顺序 = 从员工自查到 HR 配置**（员工能自己动手的先查，HR 后台配置的后查）。

```
① 手机定位（员工自查，最先）
   ├─ 精确位置未开（iPhone：设置→app→位置→精确位置；最常被忽略）
   ├─ 定位权限拒绝（设置→隐私→定位服务→app 权限）
   └─ GPS 冷启动漂移（刚从电梯/楼下出来，GPS 未校准；原地等/走动重试）

② 打卡方式（员工+HR 核对）
   ├─ 只配 WiFi 打卡未配 GPS（楼下连不上公司 WiFi）
   └─ 楼下没连公司 WiFi（即使配了 WiFi 打卡，人未进楼连不上）

③ 打卡范围配置（HR 后台查，最常见根因）
   ├─ 围栏半径过小（只覆盖楼内，楼下一步之差出界）
   ├─ 中心点/坐标偏（打卡中心点和实际办公地有偏差）
   └─ 只覆盖楼内（没把楼下出入口纳入范围）

④ 系统规则（HR 调整）
   ├─ 定位误差容忍值小（GPS 正常漂移就被拦）
   └─ 打卡时间范围限制（某些时段不允许打卡）
```

**个性化手机排查（员工视角关键——按机型定制，不是甩通用清单）**：
- **iPhone**：最常见是「**精确位置**」没开——设置→找到打卡 app→位置→确认"使用 App 期间"+「精确位置」开关打开；再查系统定位总开关（设置→隐私与安全性→定位服务）
- **安卓**：设置→应用管理→打卡 app→权限→位置信息"允许"（最好"仅使用时允许"）；部分机型需开 GPS/定位服务双开关
- 通用：让员工「完全退出 app 重开 / 下拉刷新」重新获取定位；向楼口开阔处走两步排除 GPS 漂移

**排查顺序建议（从快到慢）**：
1. 员工先自查手机（精确位置→定位权限→连 WiFi→走动重试）——排除①③类
2. 手机全正常 → 反馈 HR 查打卡范围（半径/中心点/打卡方式）——②③④类
3. 兜底：当天缺卡 → 提交补卡

**回答要点**：
- **管理员视角**：指导检查「考勤设置→打卡范围/打卡方式」，按鱼骨图②③④类逐项：围栏半径/中心点/打卡方式/误差容忍值
- **员工视角**：按机型定制自查（iPhone 精确位置/安卓权限）→ 引导补卡/联系 HR

**边界**：改打卡范围=配置操作，AI 只指导不代改；员工当天若因此缺卡，可走补卡流程。

### 鱼骨图② 没有打卡入口（入职员工，入口未生效）

把"app 找不到打卡入口"作为问题鱼头，从**五大类原因**（鱼骨刺）排查。**排查顺序 = 从 HR 配置到客户端**（新员工场景 HR 侧是主因）。

```
① APP应用配置（HR 查，★可能性最大，最先查）
   └─ APP应用管理未配置"考勤打卡"应用/未对员工可见
      账号→基础设置→APP和ESS设置→应用管理
      （若打卡应用未在 APP 应用模块启用或员工被排除在可见范围外，
       app 首页就找不到打卡入口——新入职员工最常见，见 help/fnuk248zb9trbgh3）

② 登录/入口侧（员工自查，★常见）
   ├─ 登录了试用/错误企业（登录后确认当前是"正确企业"，需切换到正式企业，
   │    试用/测试企业无打卡配置——员工新入职常见）
   └─ 三方集成入口未配置（经企业微信/钉钉/飞书进入打卡时，
       三方应用里未配置考勤应用——锚点 fnuk248zb9trbgh3：部分配置入口需对接三方才显示）

③ 入职状态（HR 查，次可能）
   ├─ 入职审批未完成（系统不认"在职"，不产生打卡入口）
   ├─ 人事档案未生效 / 工号未生成
   └─ 账号未同步到考勤模块

④ 考勤配置（HR 查，次可能）
   ├─ 未分配到考勤组（打卡入口基于考勤组，没进组不显示）
   ├─ 未排班/无班次（无排班也可能不显示入口）
   └─ 打卡方式未开通（被设置为"仅考勤机打卡"，app 不显示入口）

⑤ 客户端（员工操作，最后）
   ├─ 首次登录数据未刷新（完全退出 app 重新登录）
   └─ app 版本过旧（更新到最新版）
```

**不常见/边缘排查项**（推断，标注待验证）：
- 账号被停用/冻结（状态异常导致考勤功能不可见）
- 所属机构未配置打卡点（多机构场景下该机构无考勤规则）
- 入职时间不在当前考勤周期（周期边界，未包含入职日）
- app 缓存损坏（重登无效 → 清缓存/重装）

**回答要点**：
- **管理员视角**：按①APP应用配置→③入职状态→④考勤配置排查——先确认「账号→基础设置→APP和ESS设置→应用管理」里打卡应用已启用且对该员工可见；再确认入职审批完成/档案生效、分配考勤组、排班、开通 app 打卡方式
- **员工视角**：① 先确认登录的是**正确的正式企业**（排除试用/测试企业）② 若走三方（企微/钉钉/飞书）进入，确认三方应用里有没有考勤入口 ③ 重新登录 app 刷新数据（排除⑤）；仍无入口 → 反馈 HR 确认 APP 应用配置与入职/考勤组
- **兜底**：处理期间缺卡 → 事后补卡

### A 路径 · 管理员/HR 视角（完整根因诊断）

目标：定位"为什么日报实际出勤/打卡不符预期"，给处理指令。

1. **定位对象**：员工 staffId（#1/#2 反查）+ 日期
2. **① 看打卡记录**（#91 打卡记录）：当天有无打卡、几段、时段
3. **② 查操作日志**（#110 操作日志，`operationModule=ATTENDANCE_SIGN`）：该时间窗内打卡是否被删/改（`subjectName` 含 DELETE/OPEN_API/INSERT）
4. **③ 查公式改写**（#96/#102 自定义字段）：日报标准字段是否被自定义字段引用/重算
5. **④ 排班/班次口径**（#排班V4）：应出勤=班次决定；实际出勤小时=打卡∩班次封顶（问题1 定案）
6. **归因 + 处理**：
   - 打卡缺失/迟到 → 补卡（补卡单）/说明漏刷
   - 打卡被删/改（日志证实）→ 恢复打卡，标注操作人
   - 标准字段被改写（自定义引用）→ 说明口径差异，指导修正公式（改公式=配置操作，AI 只指导不代改）
   - 排班/班次导致 → 调整排班
   - 全天缺勤判定：无打卡 + 无补卡/请假单 → 缺勤成立（问题1 案例）

### B 路径 · 员工本人视角（AI 代查，直接给答案）

目标：回答"我为什么异常"，引导自助处理。**不要求员工调接口，AI 代查后直接给答案**。

1. **身份**：staffId = 宿主当前登录人（页面/上下文自带），不走"查员工 ID"
2. **查本人日报/打卡**（#93/#94/#91 按本人 staffId）
3. **直接给答案**（示例）：
   - "你 8月6日 09:30 无打卡记录，当天判定缺勤"
   - "你当天有 1 段打卡但未达班次要求，实际出勤 4.2 小时"
4. **引导自助处理**：
   - 无打卡/漏刷 → "请在【我的考勤】提交补卡申请"
   - 忘记签到/请假 → "可提交请假单/说明"
   - 数据有疑问 → "请联系 HR 复核，或 HR 端可查原始打卡"
5. **边界**：
   - **不展示**操作日志（#110）、公式配置（#96）——员工不该看"谁改了什么"
   - **不查他人数据**
   - 不下管理指令（补卡审批、恢复打卡等是 HR 权限）

**流程节点结构（节点为 childNode 链表）**：

- `advancedSettingVo`：allowBackProcess（退回）/ allowWithdrawProcess（撤回）/ noApproverOperation（无审批人转 ADMIN/部门主管）

**★ 节点递归规则（2026-08-13 补，宿主 AI 必读，避免漏分支）**：
1. **每个节点都递归 childNode**（除非 null/结束）
2. **ParallelGateway 必须遍历 conditionNodes 下每个 ParallelFlow**（★关键），并对每个 ParallelFlow 递归其 childNode（HandleTask/Task 等实际节点）——**不要在 ParallelGateway 停下**，否则漏掉并行分支里的办理人/审批人
3. **Gateway 遍历 conditionNodes 下每个 Flow**（按 flowPriority 取首个命中）
4. **AggregationGateway 递归其 childNode**（并行汇聚后的下一个节点）
5. **Flow/ParallelFlow 递归其 childNode**（分支命中的实际节点）
> 详情与补卡 P3 反例见 `api-handbook/08-审批相关/审批类型设置-流程定义.md`「★★★ 节点递归规则」。

条件分支命中 → Flow.childNode → ParallelGateway（nodeName="并行网关"）
   ├─ conditionNodes[]（多路并行，同时推进）
   │    ├─ ParallelFlow "条件1"（flowPriority=1）: 条件（如 发起人姓名 IN [员工G]，
   │    │    condActivitiType=INITIATE_STAFF + nodeUserSettings 人员列表）
   │    │    → childNode: Task（会签：指定员工 员工A、员工X）
   │    └─ ParallelFlow "默认"（flowPriority=2, OTHER）: 其他条件
   └─ childNode → AggregationGateway（nodeName="分支聚合"）← 并行在此汇聚
```
**并行 vs 条件（区分要点）**：条件 Gateway 多分支**互斥**（按 flowPriority 顺序判断走其一）；并行 ParallelGateway 多分支**同时执行**，最后在 AggregationGateway **聚合**。判断依据既可是表单字段（componentId），也可是发起人维度（condActivitiType=INITIATE_STAFF + nodeUserSettings 人员集合）。

**条件运算符枚举（conditionType）**：LT（小于，condValue 存阈值）/ IN（包含，nodeUserSettings 存人员集合）已实测；数值/日期类（GT/EQ/GE/LE）待补。

**关键认知（用户确认）**：**流程与表单字段有关系**——条件分支的判断依据就是表单字段（`flowConditionSettings.componentId` ↔ `formVo.formDetail[].id`，如 startTime__endTime__total）；并行分支还支持发起人/人员维度（INITIATE_STAFF + nodeUserSettings）。解释"为什么走 A 分支" = 该单字段值命中条件规则。

**★ 员工→适配流程（反向匹配，2026-08-10 打通）**：已知某员工，拎出"他发起某审批会走哪条分支、谁审批"：
```
1. 员工属性：OpenAPI auth/v1/group/approval（审批流权限分组=员工分组）→ 建 staffId → [分组名] 映射
               + #2 员工详情（departmentName/positionName/superiorsInfo 汇报链）
