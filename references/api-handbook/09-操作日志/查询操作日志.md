# 查询操作日志（#110）

## 基本信息

| 项目 | 内容 |
|------|------|
| 接口编号 | #110 |
| 接口名称 | 查询操作日志列表 |
| 接口地址 | `POST /openapi/thirdparty/api/operationlogs/v1/api/query/ids` |
| 请求方式 | POST |
| 鉴权方式 | Bearer Token |
| 路径前缀 | `/openapi/thirdparty/api/operationlogs/v1/`（与考勤 tm 系列不同） |
| 创建时间 | 实测录入 2026-07-31 |
| 创建人 | WorkBuddy |
| 最近更新 | 2026-07-31（实测 data 为分页对象，非官方文档所标 Boolean） |

---

## 接口定位

跨模块审计/溯源接口。通过 `operationModule` 指定业务模块（考勤打卡、任务管理等），按时间窗查询该模块下的操作记录（新增/编辑/删除/OpenAPI 接入等），用于排查"数据为何对不上"——例如定位某时段内的打卡记录是否被 HR 删除或 OpenAPI 改写。

> 与考勤取数接口（#91~#102）的区别：本接口只返回**操作动作与目标名称**（`subjectName`），**不含员工姓名/具体字段值**；要落到具体人，需结合 #91 打卡记录交叉定位。

---

## 请求参数

| 参数 | 位置 | 类型 | 必填 | 限制 | 备注 |
|------|------|------|------|------|------|
| companyId | body | String | 是 | - | 企业/租户 ID（如 `01-xxxxxxxxxxxxxxxxxxxxxx`） |
| page | body | int | 是 | 从 1 开始 | 页码，**注意：与考勤 tm 系列（从 0 起）不同，此处从 1 起** |
| size | body | int | 是 | 正整数，最大 100 | 每页条数 |
| sort | body | List\<String\> | 否 | - | 排序字段，如 `["operationTime"]` |
| operationModule | body | String | 是 | 见枚举 | 操作模块（决定查哪类业务日志） |
| operationType | body | String | 否 | 见枚举 | 操作类型过滤（不传则返回该模块全部类型） |
| subjectName | body | String | 否 | - | 操作目标名称模糊匹配 |
| operationTimeRangeStart | body | String | 是 | ISO8601 含时区 | 操作时间起，如 `2026-07-25T00:00:00+08:00` |
| operationTimeRangeEnd | body | String | 是 | ISO8601 含时区 | 操作时间止，如 `2026-07-31T23:59:59+08:00` |

## 请求示例

```json
POST /openapi/thirdparty/api/operationlogs/v1/api/query/ids
Content-Type: application/json;charset=UTF-8
Authorization: Bearer access_token

{
  "companyId": "01-xxxxxxxxxxxxxxxxxxxxxx",
  "page": 1,
  "size": 20,
  "sort": ["operationTime"],
  "operationModule": "ATTENDANCE_SIGN",
  "operationTimeRangeStart": "2026-07-25T00:00:00+08:00",
  "operationTimeRangeEnd": "2026-07-31T23:59:59+08:00"
}
```

## 响应数据

| 参数 | 类型 | 父节点 | 备注 |
|------|------|--------|------|
| code | int | Response Body | 状态码，0=成功 |
| message | String | Response Body | 提示信息 |
| errorResult | Boolean | Response Body | 错误标识 |
| data | JSONObject | Response Body | **分页对象**（见下；官方文档误标为 Boolean） |
| totalPages | long | data | 总页数 |
| totalElements | long | data | 总记录数 |
| end | Boolean | data | 是否末页 |
| content | JSONArray | data | 操作日志列表 |
| id | String | content | 操作日志 ID（数值型字符串，如 `1133964610173665280`） |
| subjectName | String | content | 操作目标名称（通用描述，不含员工姓名） |

> ⚠️ **官方文档勘误**：OpenAPI 官方文档将 `data` 响应参数类型标注为 Boolean（"是否更新成功"），**实测 `data` 为分页对象**（含 totalPages/totalElements/end/content）。以本手册实测为准。

## 枚举值

### operationModule（操作模块，部分）

| 值 | 含义 |
|----|------|
| ATTENDANCE_SIGN | 考勤打卡 |
| TASK_MANAGEMENT | 任务管理 |

> 其他业务模块枚举值以官方文档/实际返回为准，持续补充。

### operationType（操作类型）

| 值 | 含义 |
|----|------|
| VIEW | 查询 |
| INSERT | 新增 |
| UPDATE | 编辑 |
| DELETE | 删除 |
| IMPORT | 导入 |
| EXPORT | 导出 |
| OPEN_API | OpenAPI 接入 |
| BUSINESS_ARCHIVE | 业务归档 |

---

## 典型用法（考勤异常溯源）

当日报/月报的"实际出勤/打卡"与预期不符、怀疑数据被改动时：

1. 用本接口查对应时间窗内 `operationModule = ATTENDANCE_SIGN` 的全部操作；
2. 重点看 `subjectName` 是否含 `DELETE`（如"通过OpenApi删除了打卡记录"）、`OPEN_API`、或 `INSERT`（如"HR新增考勤了打卡记录"）——这些动作会改变打卡原始数据；
3. 若 `subjectName` 仅为"流程审批补卡单通过"等且无删除/改写类动作，则打卡未被人为改动，异常应从班次/排班口径排查；
4. 本接口 `subjectName` 不含员工姓名，需拿 `id`/时间窗回查 #91 打卡记录接口，落到具体员工与时间点。

> 实测样例（某员工 2026-07-25~07-31 时间窗）：返回 4 条 ATTENDANCE_SIGN 记录，均为"流程审批补卡单通过"与"HR新增考勤了打卡记录"，**无 DELETE/OPEN_API 删除类**，可确认该时段打卡记录未被删除改写。
