## 二、★ 鉴权边界实测（重要）

| 接口 | 鉴权方式 | 实测结果 |
|------|---------|---------|
| OAuth 换 token（POST /openapi/oauth/token） | Basic AppID:AppSecret | ✅ 200，`access_token` 直接返回（非 data 嵌套） |
| **二方流程定义 draft（/gateway/workflow/...）** | **Cookie+XSRF 或宿主 IHR360_API_TOKEN** | ❌ **OAuth Bearer → 401 "会话过期"**——证实二方 Gateway 与 OpenAPI 不互通 |
| #1 员工ID清单（OpenAPI） | Bearer | ✅ 200（62 名在职） |
| #88 出差单（OpenAPI） | Bearer | ✅ 200（7 条） |
| #106 已完成单据（OpenAPI） | Bearer | ✅ 200（2 条，需 source 跨年） |

> **★ 结论**：流程定义（draft/已发布）仍必须走宿主登录态；但**单据实例（#88/#106）用 OAuth 全通**——问题5 三要素中"流程定义"靠宿主取**当前生效版本**，"单据实例+字段值"可 OAuth（单据实例仅用于验证实际走向/审批结果，**不能替代流程定义**；流程定义更新后历史单据 ≠ 当前流程）。

## 四、单据实例（#106 taskInfoList 实测）

```
出差单 appCode=202512150003（申请人=员工A, PASS, processUniqueId=992311760633737216）
审批节点：HR:员工A | 同意 |（单节点）
出差单 appCode=202509010002（申请人=员工A, PASS）
审批节点：员工A | 同意 |（单节点）
```

> **★ 单据侧 vs 流程定义侧的分工**：#106 只返回**实际发生的审批节点**（谁在什么时间同意/驳回），不返回"配置了哪些节点/条件/会签"（那是 draft 的职责）。单节点=该单实际只走了一级审批，不代表流程定义无更多节点——**解释"为什么走这条路"必须两者结合**。

## 五、★ source 跨年机制实测（#106 关键）

| source 传参 | 返回 | 说明 |
|------------|------|------|
| 不传 / main | totalElements=0，**reset=true**，返回 source=2026 | 当前年数据源，无出差单据则 0 条 |
| "2025" | totalElements=2，含 2 条 PASS | **跨年查询必须显式传 source=年份** |
| "2026" | totalElements=0，reset=true，返回 source=2025 | 传了非当前年也返回别的？——**reset 语义：传 source 后需按返回的 source 重新发起查询** |

> 文档原描述"source 数据年份源：空/main=当前，也可传 2023 等跨年查询"——实测确认：**传具体年份才能查到该年数据**，且响应里的 `reset` 与 `source` 字段是查询状态指示。
