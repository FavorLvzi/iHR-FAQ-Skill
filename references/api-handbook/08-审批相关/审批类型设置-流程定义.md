# 审批类型设置-流程定义（二方，问题5 核心）

## 基本信息

| 项目 | 内容 |
|------|------|
| 接口名称 | 获取审批类型设置（流程定义） |
| 首选接口 | `GET /gateway/workflow/aggregate/approval/setting/{approvalSettingId}`（★已发布版本，2026-08-11 实测确认） |
| 草稿接口 | `GET /gateway/workflow/aggregate/approval/setting/draft/{approvalSettingId}`（草稿版本，可能被并发保护锁定） |
| 请求方式 | GET |
| 鉴权方式 | Cookie+XSRF（前端插件）/ 宿主 AI 环境 `Authorization: Bearer {IHR360_API_TOKEN}`（OAuth Bearer ❌ 401，见下） |
| Host | `v5.ihr360.com` |
| 实测时间 | 2026-08-07（草稿）/ 2026-08-11（★已发布） |

> 返回某审批类型（请假/外出/补卡等）的**完整配置**：谁能发起、表单字段、流程节点（含条件/并行分支）、高级规则——**问题5"流程走向分析"的流程定义来源**。

> **⚠️ approvalSettingId 因环境而异**：不同公司/环境（companyId）下同一审批类型的 `approvalSettingId` 不同——如补卡在 A 环境 = `b69494b9-...`、B 环境 = `e725ca53-...`、C 环境 = `25c6c946-...`/`a0a81a55-...`（2026-08-11/08-12 实测观察到多个值）。**每次使用前先调 `findApprovalGroupVo` 按 name 拿当前环境的 id，不要硬编码**。
>
> **⚠️ 列表 id vs setting 响应 data.id 可能不同（2026-08-12 宿主解读暴露）**：宿主 AI 实测中 `findApprovalGroupVo` 列表返回补卡 id=`a0a81a55-...`，而 `approval/setting/{id}` 响应 `data.id`=`6ac24d12-...`——两者不同。**以 findApprovalGroupVo 列表的 id 为准**（交叉验证过的路径参数），setting 响应里的 `data.id` 是内部主键/或解析差异，不要用它回查。

## ★★ 已发布 vs 草稿（2026-08-11 关键区分，★首选已发布）

| 端点 | 路径 | 说明 |
|------|------|------|
| **已发布**（首选） | `approval/setting/{id}` | **直接返回已发布版本，不受草稿锁影响**（实测返回 201KB 完整定义，含 basicSettingVo/formVo/processSettingVo/advancedSettingVo 4 大块） |
| 草稿 | `approval/setting/draft/{id}` | 可能被并发保护锁定（"已被其他管理员修改"），或返回**草稿版本**（≠正式版） |

> **★ 实战教训（2026-08-11）**：补卡样例此前用草稿（draft/18129eb8）——条件3 只有"会签测试员工Y"单节点；但系统正式版里条件3 下还有**嵌套并行**（员工=员工X→办理人员工I / 员工X→办理人员工J + 分支聚合）——**草稿 ≠ 正式版，查流程走向必须用已发布接口**。

## ⚠️ 鉴权与并发保护（2026-08-07 宿主实测，重要）

| 鉴权方式 | 实测结果 |
|---------|---------|
| 前端插件 Cookie+XSRF | ✅ 正常（用户抓包成功拿到请假/外出） |
| 宿主 AI 环境 `IHR360_API_TOKEN` | ✅ 已发布接口实测可用（2026-08-11） |
| **OpenAPI OAuth Bearer** | ❌ **401"会话过期"**——二方 Gateway 与 OpenAPI 不互通，已证实 |

**★ 草稿并发保护（仅草稿端点受影响）**：draft 接口返回**草稿视图**，若流程存在**未发布草稿**（被其他管理员修改/有未保存编辑），调 `draft/{正式ID}` 返回业务错误：
```
code=-1, message="抱歉，该流程已被其他管理员修改，请退出重新进入设置！"
```
- 2026-08-07 宿主实测：请假/补卡/出差 **全部**返回该拦截（含之前成功的请假）——说明保护是**全局草稿状态**相关，不是特定类型问题
- **★ 已发布端点不受此影响**：`approval/setting/{id}` 直接返回已发布版本，无需解锁
- **对 AI 的影响**：**首选已发布接口**（无锁、最新正式配置）；draft 仅在需查"未发布编辑内容"时才用（配合 hasUnPublishDraft 解锁）
- **应对**：先调 `approval/setting/{id}` 拿正式配置；如需看草稿编辑内容 → hasUnPublishDraft 拿草稿ID → draft/{草稿ID}

**★ 解锁机制（hasUnPublishDraft，2026-08-07 用户抓包发现）**：
```
GET /gateway/workflow/aggregate/approval/setting/hasUnPublishDraft/{approvalSettingId}
→ { "hasUnPublishDraft": true, "draftSettingId": "114aaece-74c6-42f9-9b86-b2634a530213" }
```
- `hasUnPublishDraft=true` → 存在未发布草稿，**返回 `draftSettingId`（草稿ID）**
- **推断**：用 `draftSettingId` 调 `draft/{draftSettingId}` 即可绕过"已被修改"拦截，拿到草稿内容（待实测确认）
- **AI 使用路径**：draft 被拦截 → 先调 hasUnPublishDraft 拿草稿ID → 再调 draft/{草稿ID}
- ⚠️ 注意：宿主 Cookie 有有效期（JWT exp 约 2h），长时间会话需重新获取

## 流程节点结构（processSettingVo，核心）

**节点为链表结构**：`childNode` 指向下一节点，顺着链表即可重构完整流程走向。

### ★★★ 节点递归规则（硬性指令，2026-08-13 补，宿主 AI 必读）

解析流程时**必须按以下规则递归**——缺一就会漏分支：

1. **每个节点都要读 childNode**：除非为 null 或单节点结束，**永远递归 childNode**
2. **遇到 ParallelGateway → 必遍历 `conditionNodes` 下每个 ParallelFlow**（★关键，不要在 ParallelGateway 就停）
   - 每个 ParallelFlow 也有 **childNode**（实际节点：通常是 HandleTask 办理人 / Task 审批）
   - 多路并行**同时执行**，最后在 **AggregationGateway** 聚合
3. **遇到 Gateway → 遍历 `conditionNodes` 下每个 Flow 分支**（按 flowPriority 取首个命中）
4. **遇到 AggregationGateway → 递归其 childNode**（并行汇聚后的下一个节点）
5. **遇到 Flow/ParallelFlow → 递归其 childNode**（分支命中的实际节点）

> **反例（宿主 AI 漏掉的场景）**：补卡 P3 会签指定员工节点里有 ParallelGateway，AI 递归到 ParallelGateway 就停了——**没继续进 ParallelFlow.childNode**，所以漏掉了"姓名含员工X→办理人员工I""姓名含员工D→办理人员工J"等并行分支的办理人。
>
> **正解**：遇到 ParallelGateway 必须遍历 conditionNodes 下每个 ParallelFlow，并对每个 ParallelFlow 递归其 childNode（HandleTask）。

### 节点类型（nodeType）

| 值 | 含义 |
|----|------|
| Start | 开始节点（发起人） |
| Task | 审批任务节点 |
| **HandleTask** | **办理人节点（★2026-08-11 正式版实测新增）**——"办理人"语义（非审批），结构同 Task（signType/approverType/remark/nodeUserSettings），多用于并行分支内的实际处理人 |
| ManualTask | **抄送人节点**（抄送指定员工/员工分组，非审批） |
| Gateway | **条件节点**（网关，含 conditionNodes 分支列表） |
| Flow | 条件分支内的流向节点（条件1/默认，flowType=COMMON 普通 / OTHER 其他/默认） |
| ParallelGateway | **并行网关**（多路并行 Gateway，含 conditionNodes 分支列表） |
| ParallelFlow | 并行分支内的流向节点（条件1/默认，结构同 Flow） |
| AggregationGateway | **聚合网关**（并行分支汇聚点，位于 ParallelGateway.childNode） |

### 审批方式（signType）——并行分支

| 值 | 含义 |
|----|------|
| SEQUENT_SIGN | 依次签（顺序审批，单级） |
| JOINTLY_SIGN | **会签**（所有审批人共同审批，并行模式） |
| **TURN_SIGN** | **依次审批：连续多级**（如"从直接汇报对象到第三级"，配合 REPORT_TO/DIVISION_DIRECTOR） |
| **SINGLE_SIGN** | **单人审批**（★2026-08-12 事假文档补充：指定单个审批人即可） |

### 审批人规则（nodeUserSettings.approverType）

| 值 | 含义 |
|----|------|
| APPLICANT_OPTIONAL | 发起人自选（optionalStaffType=OPTIONAL_STAFF_ONE 单选/多选） |
| POSITION | 指定职位（approverPositionType=POSITION，如"CEO"） |

| **DIVISION_DIRECTOR** | **部门负责人（连续多级）**——如"从直接部门负责人到第五级部门负责人(从下至上/从上至下)" |

### ★ 条件分支（Gateway 节点，问题5 核心）

```
Gateway 节点（nodeType=Gateway, nodeName="condition"）
└─ conditionNodes[]（分支列表，flowPriority 小的先判断）
   ├─ { flowType: COMMON（普通条件）, flowPriority: 1, remark: "共计时长<1",
   │    flowConditionSettings: [{ title:"共计时长", componentId:<表单字段id>,
   │                              conditionType:"LT", condValue:"1" }],
   │    childNode: <该分支命中的后续节点> }
   └─ { flowType: OTHER（默认分支/其他条件）, flowPriority: 2, remark: "其他条件",
        flowConditionSettings: [] }
```

**flowConditionSettings 条件规则字段**：

| 字段 | 说明 |
|------|------|
| title | 判断的字段名（来自表单） |
| componentId | **关联 formVo 表单字段 id**（如 1138002290008006662 = startTime__endTime__total）——**条件分支的判断依据就是表单字段** |
| conditionType | 运算符：LT 小于 / IN 包含（见下） |
| condValue | 阈值 |
| condActivitiType | 条件来源类型：`SOURCE_ACTIVITI`（系统预置，如 INITIATE_STAFF 发起人）+ `condBtnType:SOURCE_ACTIVITI`；或 `SOURCE_FROM`（表单字段）+ `condBtnType:SOURCE_FROM` |
| nodeUserSettings | 条件命中值（当条件是"发起人 ∈ 指定人员"时，这里是人员列表，dataName=姓名） |
| seqNo | 条件序号 |

**条件运算符枚举（conditionType）**：

| 值 | 含义 | 条件值载体 |
|----|------|-----------|
| LT | 小于（数值比较，如 共计时长<1） | condValue=阈值 |
| IN | 包含（枚举/人员判断，如 发起人姓名 ∈ [员工G]） | nodeUserSettings[] 携带成员列表（dataName=姓名），title 显示字段名 |

> 数值/日期类条件用 condValue 存阈值（如 LT/GT/EQ/GE/LE）；人员/枚举类用 nodeUserSettings[] 存集合（IN/含）。

### ★ 并行分支（ParallelGateway 节点，多路并行，问题5 扩展）

```
Gateway（condition）命中某分支后
└─ Flow.childNode → ParallelGateway（nodeType=ParallelGateway, nodeName="并行网关"）
     ├─ conditionNodes[]（并行分支列表，多路同时执行）
     │    ├─ ParallelFlow "条件1"（flowPriority=1, COMMON, remark:"发起人姓名包含员工G",
     │    │    flowConditionSettings: [{condActivitiType:INITIATE_STAFF, title:"姓名",
     │    │                              conditionType:"IN", nodeUserSettings:[{dataName:"员工G"}]}],
     │    │    childNode: Task（会签：指定员工 员工A、员工X））
     │    └─ ParallelFlow "默认"（flowPriority=2, OTHER, remark:"其他条件"）
     └─ childNode → AggregationGateway（nodeType=AggregationGateway, nodeName="分支聚合"）
          ← 并行分支在此汇聚，之后继续下一节点
```

**并行 vs 条件（区分要点）**：
- **条件 Gateway**：多分支**互斥**，按 flowPriority 顺序判断，命中其一即走单一路径。
- **并行 ParallelGateway**：多分支**同时执行**（如"发起人是员工G"走一条、"其他人"走另一条，两条并行推进），最后在 **AggregationGateway** 汇聚合并。
- 两者都用 `conditionNodes[]` 承载分支，靠 `nodeType`（Gateway/ParallelGateway）+ `flowType`（COMMON/OTHER）区分。

> **"流程与字段的关系"（用户确认）**：条件分支的判断字段 = 表单字段（formVo.formDetail[].id ↔ flowConditionSettings.componentId）；并行分支还支持发起人/人员维度（condActivitiType=INITIATE_STAFF + nodeUserSettings 人员列表）。解释"这张单为什么走这条分支"，需要 流程定义（本接口的条件规则）+ 单据实例（#106）+ 字段实际值 三要素。

## 实测样例

### 请假单（含条件分支 + 并行分支，2026-08-07 完整实测）

```
Start（发起人）→ Task（会签：发起人自选, signType=JOINTLY_SIGN）
  → Gateway（condition）
      ├─ 条件1（flowPriority=1, COMMON）: 共计时长 LT 1
      │    └─ Task（会签：指定职位"变更后的职位", approverType=POSITION）
      │         └─ ParallelGateway（并行网关）
      │             ├─ 条件1（COMMON）: 发起人姓名 IN [员工G]（condActivitiType=INITIATE_STAFF）

      │             └─ 默认（OTHER）: 其他条件
```
